Pagination and infinite scroll

How pages are requested, when the next one starts, what happens on errors and how to start over.

The loadData contract

TSX
type LoadData = (
  page: number, // starts at 1 and increases by 1 for every successful request
  pageSize: number,
) => Promise<{ data: any[]; hasMore: boolean }>;

The component keeps all loaded items. Return only the new page from loadData; the library appends it. Page numbers are tracked inside the component, you do not have to count them.

When the next page starts

A 1px marker sits at the bottom of the layout. An IntersectionObserver with rootMargin: loadMoreThreshold watches it, so the next request starts when the bottom is loadMoreThreshold px away from the viewport. After every page finishes the observer is subscribed again, which re-checks the current state: if the marker is still near the viewport (a fast scroll outran the content) the next page starts immediately.

  • Raise loadMoreThreshold if users scroll fast or your API is slow.
  • Make sure pageSize fills more than a screen. With very small pages the marker stays visible after each response and requests chain one after another.

One request at a time

A new request never starts while another is running. The guard is synchronous, so even a burst of triggers in the same frame results in a single request, and responses cannot arrive out of page order.

When a request fails

A rejected loadData is logged with console.error and automatic paging stops (hasMore becomes false). This prevents a broken endpoint from being called in an endless loop while the marker is still visible. Choose how you want to recover:

  • Remount the component with a new key to start again from page 1.
  • Catch errors inside your loadData and return { data: [], hasMore: true } after your own retry logic, if you want paging to continue.

Starting over when filters change

The component loads page 1 on mount and never reloads by itself. When the query changes, remount it:

TSX
<VirtualMasonry
  key={JSON.stringify(filters)}
  loadData={(page, size) => fetchImages({ ...filters, page, size })}
  renderItem={renderCard}
/>

With DynamicMasonryView

DynamicMasonryView calls page 1 itself to find the layout type and hands that response to the inner layout, so page 1 is requested once. Changing the controlled isMasonry prop remounts the inner layout and requests page 1 again.

Unique items

The library does not remove duplicates. If your API can return the same record on two pages (for example when new items are inserted while the user scrolls), de-duplicate inside loadData and keep key stable and unique.
