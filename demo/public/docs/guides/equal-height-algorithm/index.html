How the equal-height layout works

A step-by-step description of the row filling algorithm with an example computed from real numbers, useful when tuning maxStretchRatio and sizeRange.

Input

Each item has an aspect ratio r = width / height. Computed at the target row height H, an item's ideal width is r * H. These are the symbols used:

SymbolMeaningMatching option
WContainer widthMeasured automatically
gSpace between itemsgap
HTarget row heighttargetRowHeight
[minH, maxH]Allowed row height rangesizeRange
maxStretchThe largest enlargement a row acceptsmaxStretchRatio
maxWMaximum width of one imagemaxItemWidth

A complete example

All numbers below are computed with the same rules as the component. Setup: container width W = 640, gap g = 6, target row height H = 90, sizeRange = [80, 100], maxStretchRatio = 1.5. Images arrive in order with the aspect ratios 3:2, 2:3, 4:3, 1:1, 16:9, ...

1. Build a row greedily

Start a row with the next image. Before adding another image, compute the scale needed to make the current row fill the container:

Text
scale = (W - (n - 1) * g) / sum(r_i * H)   // n images in the row
  • If scale <= maxStretchRatio the row is full enough and ends.
  • Otherwise add the next image and check again. Adding an image always brings the scale closer to 1.
  • If the row already needs to shrink (scale < 1) it ends as well; shrinking is not limited.

This is how the first row goes:

Images added so farRow width Σ r·HAvailable width W - (n-1)·gScale scaleDecision
3:21356404.744.74 > 1.5: add another
3:2, 2:31956343.253.25 > 1.5: add another
3:2, 2:3, 4:33156281.991.99 > 1.5: add another
3:2, 2:3, 4:3, 1:14056221.541.54 > 1.5: add another
3:2, 2:3, 4:3, 1:1, 16:95656161.091.09 ≤ 1.5: end the row

The first row takes 5 images. Because a single image almost always needs a very large enlargement to fill a row, this rule needs no special case to guarantee at least two images per row.

2. Compute and clamp the row height

Text
rowHeight = H * scale
rowHeight = clamp(rowHeight, minHeight, maxHeight)   // sizeRange

First row: rowHeight = 90 × 1.09 ≈ 98.1, which is within [80, 100], so the row height is 98.

sizeRange is an independent visual density limit, so it always applies. When the clamp prevents an exact fill, the next step still makes the row end at the edge.

3. Distribute widths without accumulating error

The ideal width of each image is r_i * rowHeight. To make the row end exactly at the container edge, the right edge of image i is computed from the cumulative share of the ideal widths and then rounded:

Text
available = W - (n - 1) * g
rightEdge_i = (sum(ideal_0..i) / sum(ideal_all)) * available + i * g
width_i     = round(rightEdge_i - x_i)

The result for the first row:

ImageIdeal width r·rowHeightRight edgeFinal width
3:2147.2147.2147
2:365.4218.666
4:3130.8355.4130
1:198.1459.699
16:9174.4640.0174

The widths 147 + 66 + 130 + 99 + 174 plus 4 gaps add up to exactly the container width 640. Rounding errors do not accumulate and are not pushed onto the last image (which would make its proportions deviate visibly from the real picture). Finally every width is limited to maxItemWidth.

Where the aspect ratio deviation comes from: once the row height is clamped to sizeRange, widths are still distributed to fill the row, so the displayed width of an image is r * the row height needed to fill, while the displayed height is the clamped row height. The deviation factor is "row height needed to fill ÷ clamped row height". In the example above both are equal, so there is no deviation; only clamped rows have one. The narrower sizeRange is, the more rows get clamped and the more visible the deviation is; object-fit: cover turns it into a little cropping.

4. The last row

  • The row at the end of the loaded data is not stretched; its height is limited to between sizeRange[0] and targetRowHeight.
  • If its natural width would exceed the container, every image in the row is scaled down by the same factor: overflowScale = (W - total gaps) / total ideal width.
  • When it does not exceed it, every image keeps its natural width and the right side stays empty.
  • When the next page arrives, the former last row becomes an ordinary row and is recalculated.

5. Virtualization

Every item gets x, y, width, height and originalIndex. Only items that intersect "the viewport plus buffer" are rendered, with originalIndex as the React key. The minHeight of the container is the bottom of the last row.

The whole thing as pseudocode

Text
i = 0
y = 0
while i < items.length:
    row = [items[i]]; i += 1

    # 1. build the row greedily
    while i < items.length:
        scale = (W - (len(row) - 1) * g) / sum(r * H for r in row)
        if scale <= maxStretch: break
        row.append(items[i]); i += 1

    isLast = (i >= items.length)

    # 2. row height
    scale = (W - (len(row) - 1) * g) / sum(r * H for r in row)
    rowHeight = H * scale
    rowHeight = clamp(rowHeight, minH, isLast ? H : maxH)

    # 3. widths
    ideal = [r * rowHeight for r in row]
    if isLast:
        factor = min(1, (W - gaps) / sum(ideal))
        widths = [min(round(w * factor), maxW) for w in ideal]
    else:
        widths = rightEdges_to_widths(ideal, W, g)   # by cumulative share, no accumulated error
        widths = [min(w, maxW) for w in widths]

    place(row, widths, y, round(rowHeight))
    y += round(rowHeight) + g

Edge cases

CaseResult
A very wide panoramaIt takes a row of its own, its width is cut to maxItemWidth, and the row may end up short on the right.
Very few images, only 1 rowThat row is the last row: not stretched, and no taller than targetRowHeight.
Container width is 0 (hidden)No layout, the output is empty; recalculated once it becomes visible.
Items without width and heightThe aspect ratio is NaN and that row and everything after it is misplaced; give mapSize a fallback.
A very small upper bound of sizeRangeThe row height is clamped while widths still fill the row, so the aspect ratio deviation grows.
Appending new dataRows that are already complete do not change; only the former last row is recalculated.

Complexity and stability

  • The whole layout is one front-to-back pass in which every item is visited a constant number of times, so the cost is proportional to the number of items. Laying out 10,000 images takes milliseconds, see performance tuning.
  • The layout is deterministic: the same data, width and options always give the same result, so content does not jump while scrolling.
  • Rows are built in order and the result of a row depends only on the rows before it and its own data, which is why appending data does not affect rows that are already complete.

Tuning tips

  • Many rows with only 2 images mean targetRowHeight is too large for the container width: lower it, or relax sizeRange.
  • A very narrow sizeRange gives very even row heights but a larger aspect ratio deviation; relax it if you want more natural proportions.
  • Lowering maxStretchRatio reduces enlargement, raising it makes rows end earlier.
  • When you doubt the effect of a setting, work one row out by hand with the formulas above and compare it with the page.

FAQ

Why not use a globally optimal partitioning algorithm?

Some libraries use linear partitioning (dynamic programming) to find one optimal split of all images into rows. The drawback is that appending data changes rows that were already laid out, so content jumps while scrolling. The greedy algorithm used here builds rows one by one in order: appending data only affects the last row, content you have already seen never moves, and the work is proportional to the number of images, which suits infinite scrolling.

Why does a row contain only one image?

That image is very wide (a panorama, for example), and on its own filling the row already needs an enlargement no greater than maxStretchRatio, so the row ends there. Its width is also capped at maxItemWidth; when that cap is below the container width the row ends up short on the right.

Why are some rows slightly taller or shorter than others?

Every row has to fill the container width, and the height needed varies with the proportions of the images in the row. It is clamped to sizeRange, so row heights vary within that range. Narrowing sizeRange makes the heights more even, but increases the aspect ratio deviation of images in clamped rows.

Why do the widths always add up to exactly the container width?

Because the right edge of each image is computed directly from the cumulative share, instead of rounding every width separately and adding them up. The right edge of the last image lands exactly on the container edge, so rounding errors do not accumulate.
