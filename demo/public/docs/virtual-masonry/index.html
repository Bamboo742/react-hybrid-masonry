VirtualMasonry

A Pinterest style waterfall layout: columns have the same width, items keep their aspect ratio and go into the shortest column. Only the items near the viewport are rendered.

Overview

VirtualMasonry arranges items in columns of equal width: every new item goes into the currently shortest column, and its height follows its own aspect ratio. The column count follows the container width (or you set it), so the same data is 2 columns on a phone and can be 6 on a wide screen. It suits image walls, product feeds and content cards of different heights.

  • Columns have the same width and item heights follow the aspect ratio in your data, independent of the image download.
  • Only items within buffer pixels of the viewport are rendered, so thousands of cards do not slow the page down.
  • The next page is requested as the user nears the bottom, with a single request in flight at a time.
  • Columns and positions are recalculated when the container width changes.

Quick start

TSX
import { VirtualMasonry } from "react-hybrid-masonry";

type Pin = { id: number; url: string; title: string; width: number; height: number };

async function loadData(page: number, pageSize: number) {
  const res = await fetch("/api/pins?page=" + page + "&size=" + pageSize);
  const json = await res.json();
  return { data: json.items as Pin[], hasMore: json.hasMore as boolean };
}

export function PinBoard() {
  return (
    <VirtualMasonry
      loadData={loadData}
      pageSize={30}
      minColumnWidth={200}
      maxColumnWidth={350}
      gap={16}
      renderItem={(item) => (
        <div
          key={item.id}
          style={{ position: "absolute", left: item.x, top: item.y, width: item.width, height: item.height }}
        >
          <img
            src={item.url}
            alt={item.title}
            loading="lazy"
            style={{ width: "100%", height: "100%", objectFit: "cover", display: "block" }}
          />
        </div>
      )}
    />
  );
}
Every item needs a width and a height before it loads: the component computes positions from them. See data and sizes below.

Data and sizes

Where sizes come from

The size of each item is read from the first pair of fields that exists: width/height, w/h, imgW/imgH. Use mapSize when your data is shaped differently:

TSX
<VirtualMasonry
  mapSize={(raw) => ({ width: raw.cover.w, height: raw.cover.h })}
  loadData={loadData}
  renderItem={renderCard}
/>

The layout only uses the height / width ratio, so any unit works: pixels, or plain ratio values such as 4 and 3.

Items without valid sizes cannot be laid out: a missing width or height gives NaN, and the positions of every item after it break. If the API may omit fields, give mapSize a fallback, for example { width: raw.w || 4, height: raw.h || 3 }.

What renderItem receives

The item passed to renderItem(item, index) is your original object plus the fields below, calculated by the layout. Your own fields (url, title, ...) are kept:

FieldMeaning
xDistance from the left edge of the container (px). May be fractional.
yDistance from the top of the container (px). May be fractional.
widthThe column width (px), the same for every item in one layout. It replaces the width in your data.
heightThe height calculated from the aspect ratio (px). It replaces the height in your data.
widthRatioThe original aspect ratio width / height.

index is the position of the item among the currently rendered items. It changes while scrolling, so do not use it as a key. To keep the original dimensions, have your API use other field names such as w/h and read them through mapSize. Positions and sizes can be fractional; if you need whole pixels, round them yourself in renderItem.

Rendering cards

  • The root element you return must be absolutely positioned with the left, top, width and height you receive.
  • Give the root element a stable key, such as item.id.
  • Inside the card you are free to lay things out: image, title, buttons. The height is item.height, and the content has to fit it.
  • For images use width: 100%; height: 100%; object-fit: cover, so they do not distort when the ratio differs from the data.
TSX
const Card = React.memo(function Card({ item }: { item: Pin & { x: number; y: number; width: number; height: number } }) {
  return (
    <article
      style={{
        position: "absolute",
        left: item.x,
        top: item.y,
        width: item.width,
        height: item.height,
        overflow: "hidden",
        borderRadius: 12,
      }}
    >
      <img src={item.url} alt={item.title} loading="lazy" style={{ width: "100%", height: "100%", objectFit: "cover", display: "block" }} />
    </article>
  );
});

<VirtualMasonry loadData={loadData} renderItem={(item) => <Card key={item.id} item={item} />} />

While the width stays the same the layout result is stable, and visible items keep the same object reference as you scroll, so wrapping the card in React.memo avoids re-rendering it on scroll, see performance tuning.

Columns and column width

The column count is determined in this order:

  1. If columns is set it is used as is, and the width options no longer take part.
  2. Otherwise start with floor(container width / minColumnWidth) columns, at least 1.
  3. If maxColumnWidth is set and the columns are wider than it, columns are added one by one (up to 20) until they fit; but if one more column would make them narrower than minColumnWidth, no further column is added. When the two limits cannot both be met, the minimum wins.

The column width is (container width - gap * (columns - 1)) / columns, capped at maxColumnWidth. Here is what the same rules produce (16px gap):

Container widthminColumnWidth={200}minColumnWidth={200} maxColumnWidth={210}
320px1 cols · 320px1 cols · 210px (110px empty on the right)
480px2 cols · 232px2 cols · 210px (44px empty on the right)
768px3 cols · 245px3 cols · 210px (106px empty on the right)
1024px5 cols · 192px5 cols · 192px
1280px6 cols · 200px6 cols · 200px
1440px7 cols · 192px7 cols · 192px
1920px9 cols · 199px9 cols · 199px
  • The minimum width does not include the gap: step 2 divides the container width by minColumnWidth without subtracting gap, so the real column width can be slightly below minColumnWidth (by less than one gap). In the table, 1024px gives 5 columns of 192px while minColumnWidth is 200.
  • When maxColumnWidth takes effect the grid is left-aligned and the right side stays empty, see the FAQ below.
  • To hit the design's column count exactly at every width, use columns and pass it per breakpoint.

Placement rules

  • Each item goes into the currently shortest column; when several columns are equally tall, the leftmost of them is used.
  • Item height = column width * (original height / original width), and the gap between items (horizontal and vertical) is gap.
  • Once an item is placed it never moves: new data is only appended below the columns, so content you have already seen does not jump.
  • The minimum height of the container equals the height of the tallest column, so the scrollbar always matches the content.
The reading order of a waterfall is down the columns, not row by row from left to right. When content must be read strictly by row, use the equal-height layout.

Scrolling, virtualization and loading

  • The component follows the window scroll and reads its own position with getBoundingClientRect, so place it in a normally scrolling page. Scrolling inside a nested overflow container is not supported.
  • Items within buffer pixels above and below the viewport are rendered, and scroll position updates are throttled per frame (requestAnimationFrame), so fast scrolling stays smooth.
  • An invisible trigger at the bottom of the container requests the next page when it is loadMoreThreshold away from the viewport. Only one request is in flight at a time.
  • A failed request (a rejected loadData) stops automatic paging to avoid endless retries; remount the component to start again, see pagination and infinite scroll.

Showing a loading state

The component does not render a loading indicator itself. If you want one, keep the state in your loadData and put the indicator under the list (the container has a minimum height, so it always sits below the content):

TSX
function Board() {
  const [loading, setLoading] = useState(false);

  const loadData = useCallback(async (page: number, pageSize: number) => {
    setLoading(true);
    try {
      return await fetchPins(page, pageSize);
    } finally {
      setLoading(false);
    }
  }, []);

  return (
    <>
      <VirtualMasonry loadData={loadData} renderItem={renderCard} />
      {loading && <p style={{ textAlign: "center" }}>Loading…</p>}
    </>
  );
}

Initial data and SSR

When you already have the first page (on the server or elsewhere), pass it as initialItems. The component renders the first screen from it without requesting page 1, and the next request is page 2:

TSX
// app/pins/page.tsx (server component)
import Board from "./Board";

export default async function Page() {
  const first = await fetchPins(1, 30);
  return <Board initialItems={first.items} initialHasMore={first.hasMore} />;
}

// app/pins/Board.tsx
"use client";

import { VirtualMasonry } from "react-hybrid-masonry";

export default function Board({ initialItems, initialHasMore }) {
  return (
    <VirtualMasonry
      initialItems={initialItems}
      initialHasMore={initialHasMore}
      pageSize={30}
      loadData={(page, size) => fetchPinsFromApi(page, size)} // the first call requests page 2
      renderItem={renderCard}
    />
  );
}
Positions can only be computed once the browser has measured the container width, so the server-rendered HTML does not contain the cards. initialItems saves the request for the first screen, not the first-screen HTML. When search engines must index the content, render a crawlable list separately, see Next.js and SSR.

Setting the columns per breakpoint

TSX
import { useEffect, useState } from "react";

function useColumns() {
  const [columns, setColumns] = useState(4);

  useEffect(() => {
    const update = () => {
      const width = window.innerWidth;
      setColumns(width < 640 ? 2 : width < 1024 ? 3 : 4);
    };
    update();
    window.addEventListener("resize", update);
    return () => window.removeEventListener("resize", update);
  }, []);

  return columns;
}

<VirtualMasonry columns={useColumns()} gap={12} loadData={loadData} renderItem={renderCard} />

There is no window during server rendering, so this hook uses the desktop column count on the first render and switches after mounting. More patterns are in responsive layouts.

Controlled usage: the Core component

If your data is already managed by React Query, SWR, Redux or similar, use VirtualMasonryCore directly. It only does layout, virtual scrolling and the near-the-bottom callback: it does not fetch and it does not deduplicate requests.

TSX
import { VirtualMasonryCore } from "react-hybrid-masonry";

function Board() {
  const { pins, hasNextPage, isFetching, fetchNextPage } = usePins(); // your own data layer

  return (
    <VirtualMasonryCore
      items={pins} // every item needs a width and a height
      hasMore={hasNextPage}
      loading={isFetching}
      onLoadMore={fetchNextPage}
      renderItem={(item) => <Card key={item.id} item={item} />}
    />
  );
}
PropTypeDefaultDescription
itemsany[]requiredAll loaded data; every item needs a numeric width and height.
renderItem(item, index) => ReactNoderequiredAs above.
onLoadMore() => void–Called near the bottom. Only fires while hasMore is true and loading is false.
hasMorebooleantrueWhether more data exists.
loadingbooleanfalseWhether a request is in flight. Set it to true during the request and back to false afterwards; the component uses the change to check again whether it should keep loading.
minColumnWidthnumber200As above.
maxColumnWidthnumber–As above.
columnsnumber–As above.
gapnumber16As above.
buffernumber300Note: differs from the default of the component above (1500).
loadMoreThresholdnumber500Note: differs from the default of the component above (800).
VirtualMasonry is the Core component plus data loading, paging and mapSize handling, so the layout behaviour is identical. Core reads item.width and item.height directly and never calls mapSize; map your data first if needed.

FAQ

The column count is not what I expected.

Without columns, the count is derived from the container width: floor(container width / minColumnWidth) first, and then columns are added one by one when maxColumnWidth is set. The first step does not account for gap, so the real column width can be slightly below minColumnWidth (by less than one gap). When you need to hit the design's column count exactly at a given width, pass columns and switch it per breakpoint.

There is empty space on the right once I set maxColumnWidth.

Yes. When the column width is capped by maxColumnWidth, the whole grid is left-aligned and the right side stays empty. To center it, wrap VirtualMasonry in a container with max-width and margin: 0 auto so the container is exactly as wide as the grid, or use columns so the columns follow the container width.

Why is the order not left to right, row by row?

The rule of a waterfall layout is that each new item goes into the currently shortest column, so two consecutive items are not necessarily in the same row, and the visual reading order is down one column, then the next. If content must be read strictly row by row, use the equal-height layout or a plain CSS grid.

Cards flicker while scrolling, or the console warns about duplicate keys.

The second argument of renderItem is the position among the currently rendered items and it changes while scrolling, so it cannot be used as a key. Set a stable key on the root element you return, such as key={item.id}.

Does a card's height jump before its image has loaded?

No. The height is computed from the width and height in your data and does not depend on the image download, so the reserved size is right from the start. This requires accurate sizes on every item.

How do I restart the list when filters change?

Give the component a new key, for example key={JSON.stringify(filters)}. It is remounted and loads from page 1 again. See the pagination and infinite scroll page.

Can I insert ad slots or placeholder cards into the list?

Yes. Mix any objects that have a width and a height into the data returned by loadData; they are placed into the shortest column like every other item. Render different content in renderItem from your own field, for example item.type.
